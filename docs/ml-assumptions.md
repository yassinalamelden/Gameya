# ML assumptions: synthetic data and reliability model

> **All training data is SIMULATED.** We have no real savings-circle histories, so the
> reliability model is trained on synthetic members generated by
> `backend/app/ml/synthetic.py`. The numbers below are design assumptions, not measurements.
> Any metric we quote (for example ROC-AUC) is measured on simulated data.

## What one row is
One (member, cycle) snapshot:
- **Features:** the 7 `ReliabilityFeatures` computed only from the member's history before that cycle.
- **Label:** `1` if the member paid that cycle late.

New members with no history start at `on_time_ratio = 1.0` and `avg_days_late = 0`.

Default size: 10,000 members, seed 42, about 225k rows.

## Hidden traits (never shown to the model)
| Trait | Distribution | Meaning |
|---|---|---|
| `discipline` | Beta(2, 1), mean ≈ 0.67 | How reliably the member pays. The spread is wide on purpose: in informal circles a few members cause most late payments. |
| `shock_rate` | Beta(1.5, 12), mean ≈ 0.11 | Chance per cycle of an income shock (job, medical, family). |
| shock persistence | 0.6 | An ongoing shock continues into the next cycle with this probability. |
| account age at start | Uniform 30–1500 days | |

## Circle shape
- 1–4 past circles per member, each 6–12 monthly cycles.
- Each member's payout slot within a circle is uniform at random.

## Late-payment model
```
P(late) = sigmoid(2.5 − 8.0·discipline + 2.2·shock + 0.8·after_own_payout)
```
`after_own_payout` encodes the known ROSCA risk: once you have received the pot, you have less incentive to keep paying on time. The model never sees this flag directly.

When a payment is late:
- **Days late:** 2 + Poisson(8·(1 − discipline)).
- **Failed charge:** the subscription charge failed first with probability 0.5.
- **Invoice:** sent if the payment is 2 or more days late, matching Smart Chase invoicing at due+1d.

## Features (exactly `ReliabilityFeatures`, no demographics)
| Feature | Definition |
|---|---|
| `on_time_ratio` | on-time payments ÷ payments so far (1.0 if none) |
| `avg_days_late` | average days late **per late payment**, which measures severity rather than frequency |
| `cycles_completed` | payments made so far |
| `failed_payments` | failed subscription charges so far |
| `invoices_needed` | Smart Chase invoices so far |
| `circles_completed` | past circles finished |
| `account_age_days` | days since the Gam'eya account was created |

No age, gender, religion, nationality, income or location field is generated or used. The score is framed as *reliability inside Gam'eya*, never as a credit score.

## Calibration notes
- Results with these parameters: late rate ≈ 23%, hold-out ROC-AUC ≈ 0.82 (logistic regression, split by member).
- A first version with a narrow discipline spread, Beta(5, 2), gave AUC ≈ 0.67 because members looked too alike. We widened the spread for the reason given in the traits table, and did not choose the setting with the highest AUC.
- We changed `avg_days_late` from per-cycle to per-late-payment because it was collinear with `on_time_ratio`. That collinearity flipped the sign of the on-time coefficient, which would have broken the top-3 factor explanations.

## Reliability model
- **Model:** `StandardScaler` + `LogisticRegression`, chosen so the coefficients can be explained. The split is 80/20 **by member**, so no member appears in both training and hold-out.
- **Training:** `cd backend && python -m app.ml.reliability.train` writes `app/ml/reliability/coefficients.json`. The file is plain JSON with no pickle, and the same seed produces a byte-identical file. The runtime scorer (`scorer.py`) is pure Python and needs no sklearn.
- **Derived input `no_history`:** 1 when `cycles_completed = 0`. Without it the linear model treated "no payments yet" (`on_time_ratio` defaults to 1.0) like a perfect record and predicted 0.10 for new members, against an actual 0.17. With it, every history-length bucket is calibrated within about 1 point. It is model-internal; the contract keeps 7 features.
- **Hold-out results (simulated):** ROC-AUC 0.821, Brier 0.123. A test re-checks AUC ≥ 0.75 on members generated from a different seed.
- **Coefficients (standardised):** in the order of the features table above, then `no_history`: −0.39, +0.67, −0.09, 0.00, +0.48, −0.34, 0.00, +0.18. `failed_payments` and `account_age_days` carry almost no weight once the other features are known.

## Top-3 factors
- **Contribution:** for each feature, `coef × standardised value` on the logit scale. Positive raises the risk, negative lowers it. We show the 3 with the largest absolute contribution.
- **Labels:** each factor gets a plain-language label built only from the member's own numbers, for example "Late payments average 9 days" or "Completed 3 circles".
- **New members:** with no payments yet, the history features are defaults, not evidence, so they are merged into one factor labelled "No payment history yet".

## Fair order: published cost formula
The payout order is a deterministic Hungarian assignment (`scipy.optimize.linear_sum_assignment`) in `backend/app/ai/fair_order.py`. No LLM chooses or changes the order. For member *i* and slot *j*, where `r = j / (N − 1)` runs from 0 (first slot) to 1 (last slot):

| Term | Formula | Why |
|---|---|---|
| Late | `1.0 × months late × urgency × flex` (flex: low 1.5, medium 1.0, high 0.5) | Paying after the member's need date is the main unfairness. |
| Early | `0.1 × months early` | Money far before it's needed is a small waste of an early slot. |
| Undated need | `0.5 × (urgency − 2) × r` | Urgent undated needs pull early; relaxed ones pull late. |
| No need given | `0.2 × (1 − r)` | Members with no stated need slightly prefer later slots. |
| Reliability guard | `4.0 × p_late × (1 − r)` | Early recipients have the most incentive to stop paying, so risky members cost more early. |

- **Tie-break:** costs are compared at 0.001 resolution. Exact ties are broken by a random permutation seeded with the published `OrderProposal.seed`. One cost step is scaled by n³, larger than any sum of tie-break values, so a tie-break can never beat a cheaper order.
- **Seed:** use `derive_seed(circle_id, member_ids)`, a hash nobody chooses. A seed someone picks freely could be "shopped" to steer tied orders.
- **Determinism:** members are sorted by `member_id` first, so the input order never changes the result.
- **Published cost is need-only:** `SlotAssignment.cost` leaves out the reliability term. Otherwise anyone who knows a member's need could solve the published formula for their `p_late`.
- **Explanations:** the engine writes the opening sentence, with every name, number and date ("Sara, you are slot 2 of 6 and receive the pot on 1 December 2026."). An LLM may add **one** "why" sentence. It never sees names, IDs or dates, only a reason code and the need category. Its sentence must contain no digits, months, names, links, instructions or reliability words (`app/ai/prose_guard.py`); otherwise a fixed template is used. Explanations never mention reliability.

## Stress-test: Monte Carlo assumptions (SIMULATED)
`backend/app/ml/stress_test.py` runs 10,000 simulated circles (seed 42) per reserve level from 0% to 10%, before launch. Reliability scores are passed in payout order.

| Event | Per-cycle probability | Effect |
|---|---|---|
| Late payment recovered in grace | most late payments | none |
| One-off missed payment (grace did not recover it) | `0.15 × p_late` | That cycle is short by one contribution. The member catches up the next cycle (Smart Chase invoice or Orders v2 pay-now), which refills the reserve. A miss in the last cycle is not repaid inside the circle. |
| Dropout | `0.02 × p_late`, ×2 after the member's own payout | The member pays nothing for the rest of the circle. An average member has about a 3.5% chance of dropping out over a 6-cycle circle. |

- **Reserve:** an **upfront deposit**. Each member deposits `reserve% × pot` when joining, so the pool exists from cycle 1. We first modelled a reserve added to each payment. It could not cover an early missed payment: 5% of $100 is $5 a cycle against a $100 hole. This is a product decision recorded on 2026-10-30, and P1's collection flow and P5's contract wording need to match it.
- **Completion:** every pot is paid in full and on time, meaning no cycle's shortfall is larger than the pool. `expected_shortfall` is the average money the pool could not cover.
- **Recommendation:** the smallest reserve with completion ≥ 95%. If none reaches it, the reserve with the best completion (the smallest on ties).
- **Explanation:** the engine writes every number, including the dollar deposit per member when the circle is passed in. An LLM may add one number-free sentence of context.
- **Limits:** `n_sims` is at most 20,000 (about 115 MB peak at N = 24), and at most 21 reserve levels per request.
- **Exact arithmetic:** money is simulated in integer cents. All reserve levels reuse the same random draws, so more reserve can never lower the odds.
- **Reference results (seed 42):**
  - a circle of 6 reliable members (p_late 0.03): 82% with no reserve → 97% with a 3% reserve
  - the demo personas, including high-risk Omar: 28% → 82% at 3% → 92% at 9%. The rest is driven by dropouts, so the explanation suggests fewer members or a smaller contribution.
